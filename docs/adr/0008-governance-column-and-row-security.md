# ADR 0008: Governance - policy tags, dynamic masking, row-level security

**Status:** Accepted

## Context
Silver and Gold hold personal data (names, emails, phone numbers, dates of birth,
postcodes). Dashboards need customer-level analysis without exposing identities, and a
regional analyst should only see their own region. UK GDPR principles: data minimisation
and access on a need-to-know basis.

## Decisions
1. **Classify once, enforce everywhere: a policy-tag taxonomy** (`telco-pii`) with one tag
   per kind of personal data. Tags are attached to columns by dbt (`policy_tags:` in the
   model YAML), so a new PII column is governed in the same pull request that creates it.
   A unit test fails if a known PII column has no tag.
2. **Dynamic masking instead of masked copies.** One table, different views per identity:

   | Tag | Masking for Masked Readers | Why |
   |---|---|---|
   | email | `EMAIL_MASK` (XXXXX@domain) | domain analysis still possible |
   | phone | `LAST_FOUR_CHARACTERS` | support staff can confirm a number |
   | name / address | `SHA256` | deterministic: COUNT DISTINCT and joins still work |
   | date of birth | `DATE_YEAR_MASK` | age bands without the exact date |
   | postcode | `FIRST_FOUR_CHARACTERS` | roughly the outward code = area |
   | raw record (DQ quarantine) | `ALWAYS_NULL` | exception data is for data stewards only |

   Fine-Grained Reader (real values): `sa-transform` (it must read to transform) and the
   data steward. Masked Reader: `sa-reporting`, `sa-analyst`. Everyone else - including
   project owners - gets "Access Denied" on tagged columns.
3. **Row-level security by region** with row access policies, generated by a dbt
   post-hook from entitlements in `dbt_project.yml` (`rls_regions`). Static filters, not a
   subquery on an entitlements table: BigQuery masking only works with non-subquery
   policies. Anyone not in a policy sees zero rows, so the pipeline and dashboards get a
   `TRUE` policy.
4. **dbt applies governance on every build**, because `CREATE OR REPLACE TABLE` drops
   row access policies and policy tags. Terraform owns the classification (taxonomy, data
   policies, who may unmask); dbt owns attaching it to the tables it builds.
5. **Custom IAM role for dbt** (`telcoDbtGovernance`): only setCategory, row access
   policies and table IAM - not BigQuery Data Owner, which could also change dataset access.
6. **Table-level grants for the analyst** (`grants:` in dbt): 3 region-bearing tables only;
   facts without a region column are not shared with them at all.
7. **Bronze is not tagged.** It is raw, append-only and readable only by `sa-ingest` and
   `sa-transform` (dataset IAM). Tagging every landing schema change was judged not worth it;
   revisit if anyone else needs Bronze.

## Consequences
- `make verify8` proves each identity's view: steward sees `jane@example.com`, reporting sees
  `XXXXX@example.com`, the analyst sees masked values for North West rows only.
- Column-level security and masking work on on-demand pricing (no edition needed).
- For a few seconds during each Gold rebuild the replaced table has no row policies until
  the post-hook runs. Production options: build into a staging table and swap, or make the
  protected tables incremental (MERGE keeps policies).
- Policy tag ids live in `.env` (`make governance-env`); dbt refuses to run without them,
  so PII is never published untagged by accident.
